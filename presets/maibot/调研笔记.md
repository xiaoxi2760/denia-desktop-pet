## 3. 架构：消息怎么进来

### 3.1 总体

MaiBot 主程序（`bot.py`）内含：

1. **聊天管线**（消息归一化 → 会话计算 → 生成回复 → 发送）；
2. **经典消息服务器（Legacy）**：默认开启的 WebSocket 服务，`config/bot_config.toml` 的 `[maim_message]` 段配置，默认 `ws://127.0.0.1:8000/ws`（协议文档原话："现有适配器几乎都走这条"）；
3. **API 服务器（Additional API Server）**：需显式 `enable_api_server = true`，默认 `ws://0.0.0.0:8090/ws`，带信封/ACK/断线重发；
4. **Platform IO**：按 `platform / account_id / scope` 三个路由维度把出站消息派发给对应"驱动"（适配器或插件网关）；
5. **插件运行时**（Host + Runner 子进程）；
6. **WebUI（FastAPI，端口 8001）**。

来源：`docs zh/develop/adapters/protocol.md`（全文抓取于 `_raw/develop_adapters_protocol.md`）。

### 3.2 经典 WS 协议报文（外挂适配器走的路）

**入站**（适配器 → MaiBot）＝一条消息对象，顶层 `message_info` + `message_segment`：

```json
{
  "message_info": {
    "platform": "deskpet",
    "message_id": "114514",
    "time": 1750000000.0,
    "user_info": { "platform": "deskpet", "user_id": "10001", "user_nickname": "主人" },
    "additional_config": { "platform_io_account_id": "deskpet_bot", "platform_io_target_user_id": "10001" }
  },
  "message_segment": { "type": "text", "data": "在干嘛" }
}
```

硬性约束（协议文档 "user_info 和 group_info 一个都不能少" 警告框）：
- `user_info.user_id`、`user_info.user_nickname` 必须是**非空字符串**，否则断言异常、消息被丢弃；
- 群消息才需要 `group_info`（`group_id`/`group_name` 非空）；**不填 `group_info` 即私聊**（官方最小适配器示例正是如此判断：`adapter-minimal.py:63` `is_group = event.get("group_id") is not None`）；
- `additional_config.platform_io_target_user_id` 决定私聊出站回给谁（"私聊出站依赖 additional_config.platform_io_target_user_id 找收件人"）。

**出站**（MaiBot → 适配器）：仍是消息对象，正文通常 `message_segment.type = "seglist"`（分段数组，含 text/at/image…），要逐段翻译。

**握手**：端点 `/ws`，握手头 `platform` 必填（决定路由）；`[maim_message].auth_token` 非空时须带 `authorization` 头（令牌原文，不加 Bearer）。同一 `platform` 只保留最新连接（旧连接被顶掉）；心跳是 WS 协议层 PING/PONG（服务端 30s 一发，10s 无响应断开）。

**保留平台名**：`webui`、`bot_console`、`maisaka_cli` 不能用，要用自己的名字（本文用 `deskpet`）。

**回执**：发送成功后适配器可发自定义消息 `message_id_echo`（`{"type":"echo","echo":<MaiBot侧ID>,"actual_id":<平台真实ID>}`），非必需。

### 3.3 maim_message 客户端 API（官方最小适配器示例实测引用）

来源：`docs zh/examples/adapter-minimal/adapter.py`（全文在 `_raw/adapter-minimal.py`，官方文档自带的"最小可用 MaiBot 适配器骨架"，运行前只需 `pip install maim_message`）：

```python
from maim_message import MessageClient

client = MessageClient()
client.register_message_handler(self.on_outbound)            # 出站回调
client.register_custom_message_handler("message_id_echo", self.on_echo)
await self.client.send_message(self.build_inbound(event))    # 入站注入（直接传 dict）
await self.client.connect(url="ws://127.0.0.1:8000/ws", platform=PLATFORM, token=None)
await asyncio.gather(self.poll_loop(), self.client.run())    # connect 之后要 run()
```

`maim_message` 自身依赖含 `fastapi/uvicorn/aiohttp`（其 master 分支 pyproject），所以外挂适配器做 HTTP 服务**不需要额外装 Web 框架**（用 aiohttp 即可，aiohttp 是它自带的依赖）。注意主程序钉的是 `0.6.8`，PyPI 上 master 已到 0.7.4——适配器建议 `pip install maim_message==0.6.8` 保持同版。

### 3.4 插件网关（MessageGateway）——现行标准的接入方式

来源：`docs zh/plugin/message-gateway.md`（全文在 `_raw/plugin_message-gateway.md`）+ `zh/plugin/api-reference.md`。

- **佐证它已是现行标准**：NapCat 适配器文档明确"独立的 NapCat 适配器已停止演进并标记归档，其全部能力已并入统一 QQ 连接器"，而统一 QQ 连接器**就是一个装在 `plugins/MaiBot-SnowLuma-Adapter/` 的插件**，以 `@MessageGateway` 方式接入（`_raw/manual_adapters_napcat.md`）。
- 用法（文档原样 API）：

```python
from maibot_sdk import MaiBotPlugin, MessageGateway

class P(MaiBotPlugin):
    async def on_load(self):
        await self.ctx.gateway.update_state(gateway_name="xxx", ready=True,
                                            platform="deskpet", account_id="deskpet_bot", scope="")
    @MessageGateway(route_type="duplex", name="xxx", platform="deskpet")
    async def send_to_platform(self, message, route=None, metadata=None, **kw):
        ...  # 出站方向：Host 把要发的消息递进来
    # 入站注入：
    await self.ctx.gateway.route_message(gateway_name="xxx", message={...})
```

- `route_type`：`send`（出站）/ `receive`（入站）/ `duplex`（双向）。**`receive`/`duplex` + `ready=True` 才能注入入站消息**（`route_message()`）。
- 消息归属校验：消息顶层 `platform/account_id/scope` 必须与网关 `update_state()` 声明一致，否则被拒。
- 拦截点：入站消息可能被 `config/adapter_policy.toml` 拦下（文件不存在时等于全部放行）。
- `api-reference.md:585-588` 给了完整签名：`route_message(gateway_name, message, route_metadata=None, external_message_id="", dedupe_key="")`、`update_state(gateway_name, ready, platform="", account_id="", scope="", metadata=None)`。

### 3.5 能不能"伪造一条私聊消息交给对话管线"？

**能**，共三条路，均有官方文档/示例背书：

| 路线 | 入口 | 出站（拿回复） | 评价 |
|---|---|---|---|
| A. 外挂适配进程 | 经典 WS `/ws` + `MessageClient.send_message()`（不填 group_info 即私聊） | `register_message_handler` 回调 | 官方最小适配器示例即此模式；独立进程、故障隔离好；NapCat 旧适配器时代的主流，**至今默认开启** |
| B. 插件网关 | 插件内 `ctx.gateway.route_message()` | duplex 网关处理器收到出站消息 | **现行标准**（QQ 连接器就是这么写的）；部署最省事（拷进 `plugins/` 即可） |
| C. WebUI HTTP | `POST /api/chat/*`（本地聊天室，"WebUI 中的『与麦麦直接对话』功能"） | 同端点 | 面向浏览器 Cookie 认证设计，接口契约未在文档中详细列出，不建议桌宠依赖 |

路线 C 来源：`docs zh/develop/webui-api/index.md`（"**`/api/chat/*`**（模块 `src/webui/routers/chat/`） — 本地聊天室。WebUI 中的'与麦麦直接对话'功能通过这些端点实现"）。源码 `src/webui/routers/chat/routes.py` 开头自述"本地聊天室路由 - WebUI 与麦麦直接对话"，且依赖 `require_auth`（Cookie 认证）。

### 3.6 主动说话（桌宠 `/recent` 需要的能力）

- 插件路径有官方主动触发 API：`ctx.maisaka.proactive.trigger(stream_id=..., intent=..., reason=..., metadata=...)` ——"把 intent 写入 Maisaka 内部上下文并唤醒 Planner，让 Maisaka 基于人格、记忆、当前上下文和可用工具自行决定是否回复以及如何表达。目标聊天流必须已经存在"（`plugin/api-reference.md` maisaka 节）。配套 `ctx.chat`（"聊天流查询、打开或创建聊天流"）。
- 外挂适配器路径：MaiBot 自主产生的、路由到 `platform=deskpet` 的出站消息都会推到适配器——但**自定义平台上麦麦会不会自发主动开口，文档没有承诺**（QQ 平台的"主动私聊"工具在统一 QQ 连接器里默认关闭，见 napcat.md "工具开关归类"）。这点在方案里按"有则显示、无则空"处理，属诚实的不确定项。
- 术语说明：旧版教程里的"心流/HeartFlow"一词在 1.x 用户文档中已不再出现，但**代码里仍在**——`src/webui/routers/chat/routes.py:18` 有 `from src.chat.heart_flow.heartflow_manager import heartflow_manager`（本机抓取源码实测）。1.x 文档语境下对应的体系叫 **Maisaka**（Planner/主动任务）。

## 4. 插件系统细节（决定"能不能嵌 HTTP 服务"）

来源：`docs zh/plugin/index.md`（全文在 `_raw/plugin_index.md`）、`zh/develop/plugin.md`。

- **架构**：Host/Runner IPC——插件代码运行在**独立子进程**，通过 msgpack 编码的 RPC（UDS/TCP/NamedPipe）与主进程通信。
- **边界**（`develop/plugin.md` 原文）："**没有沙箱** — 没有通用的文件/网络隔离，插件等同于以主程序权限运行的代码"；"独立进程 — 第三方插件跑在 Runner 子进程里，主进程崩溃与插件崩溃互不牵连；单次 RPC 默认 30 秒超时"。
  - ⇒ **插件可以自行监听 TCP 端口起 HTTP 服务**（它是普通 Python 进程）。桌宠的 5 个接口完全可以由一个插件承载。
  - ⚠️ 但注意：所有**第三方插件共用一个 Runner 子进程**（plugin/index.md 架构图：Third-party Supervisor 管一个 Runner）。插件若崩溃，同 Runner 的其它第三方插件（包括统一 QQ 连接器）会被牵连。
- **插件形态**：目录 `plugins/<id>/`，必需 `_manifest.json` + `plugin.py`（含 `create_plugin()`）；SDK 要求实现 `on_load()` / `on_unload()` / `on_config_update()` 三个生命周期方法，缺一 Runner 拒载。
- **9 种组件装饰器**：`@Tool`（LLM 工具）、`@Command`（斜杠命令）、`@HookHandler`、`@EventHandler`、`@API`、`@MessageGateway`、`@HomeCard`、`@LLMProvider`、`@ReplyExtension`。
- **17 种能力代理** `self.ctx.*`：`gateway / send / db / llm / config / emoji / message / frequency / component / chat / person / render / knowledge / statistics / tool / maisaka`（+ `paths/logger` 上下文）。
- **manifest**：`manifest_version: 2`，需声明 `host_application`（主程序版本区间）与 `sdk`（SDK 版本区间）；`capabilities` 是**逐项精确比对**的能力白名单（如 `send.text`、`chat.open_session`、`maisaka.proactive`），没声明的调用会被拒（`plugin/manifest.md` + `plugin/api-reference.md`）。
- **安装**："将插件目录放入 `plugins/` 文件夹，启动 MaiBot 后插件会自动被发现和加载"（plugin/index.md §5）。
- 官方插件市场仓库：`Mai-with-u/plugin-repo`（"麦麦（MaiBot）的插件仓库"）。

## 5. 人格 / 记忆系统（把娅娅人设喂给它）

来源：`docs zh/manual/configuration/bot-config.md`（全文在 `_raw/manual_configuration_bot-config.md`，41KB 全量配置参考）。

- 所有主设置集中在 **`config/bot_config.toml`** 一个文件，首次启动自动生成，程序负责升级字段；"保持默认就能直接运行，只改你确实想调整的部分"。
- **人格三件套**（`[personality]`）：

```toml
[personality]
personality = "是一个大二女大学生，……"      # 她是谁、什么性格。1~2 句即可，太长反而稀释效果
behavior_style = "不会没话题硬找话题：……"    # 行动准则：何时插话、何时安静
reply_style = "你的风格平淡简短，……"        # 说话风格习惯
multiple_reply_style = ["……", "……"]        # 备用风格（配合 multiple_probability 随机切换）
multiple_probability = 0
```

- **名字**（`[bot]`）：`nickname = "麦麦"`（自称/显示名）、`alias_names = []`（别称，辅助识别提及）。桌宠场景应改成"娅娅"。
- **聊天上下文**（`[chat]`）：`max_private_context_size = 60`（私聊参考最近消息数）、`max_context_size = 40`（群聊）、`mid_term_memory = true` + `mid_term_memory_lenth = 10`（"聊天回想"，注意 `lenth` 是官方保留的历史拼写，改成 `length` 会被当未知字段清理）。
- **发言频率**（`[chat.reply_timing]`）：`talk_value`（群聊）、`private_talk_value`（私聊，越小越安静）——桌宠是私聊场景，想让娅娅"有问必答"就保持 1.0，想让她偶尔装没听见就调低。
- **长期记忆 A_Memorix**：独立子系统，"最简启用只需两行"（`[A_Memorix]` 下 `enabled = true` + 嵌入模型可用），12 个子段落详见官方 `amemorix-config.md`。
- **WebUI 也有记忆管理页**（`zh/manual/webui/memory-management.md`）与 REST 接口（`/api/webui/memory/*`、兼容路由 `/api/graph`、`/api/episodes`、`/api/import` 等——webui-api/index.md）。
- **每聊天流专属 Prompt**：WebUI 聊天室源码中存在 `ChatPromptUpdateRequest`（"聊天流专属 Prompt 编辑请求"，`src/webui/routers/chat/routes.py`），即可给桌宠这条聊天流单独加 prompt（文档未系统化，列为线索）。
- 结论：**桌宠要喂"娅娅人设"，改 `[bot].nickname` + `[personality]` 三行就能起步**；更深的口吻一致化靠 `reply_style` 与 A_Memorix 记忆积累。

## 7. 与桌宠对接的契合度分析

### 7.1 桌宠契约回顾（以接口总览.md 为准）

- 5 接口：`GET /api/status`；`POST /api/socialV2/pet-chat`（核心，body 实际**只有 `key`+`text`**，旧文档的 `image`/`timeoutMs` 桌宠从不发送——不一致清单 D8）；`GET /api/socialV2/recent`；`POST /api/socialV2/screen-permission`；`POST /api/socialV2/voice-preview`。
- `pet-chat` 同步阻塞，桌宠硬超时 90s，后端须在 90s 内返回（超时也返回 `"reply":""`）；空串=她选择沉默，属正常。
- 响应里 `recent` 必须**恒为 `[]`**，且本轮 `reply` 不要再写进 `/recent`（高水位去重机制，见接口总览.md §5.2 红色警告）。
- `/recent` 的 `ts` 必须毫秒、严格递增且唯一。
- 桌宠恒拨 `http://127.0.0.1:{tunnelLocalPort}`（默认 **13100**）——`electron/main.cjs:33` `const BASE = \`http://127.0.0.1:${TUNNEL_PORT}\``（本机读源码实测）。

### 7.2 任务描述与代码的一处矛盾（已查证）

任务说"`sshHost`（同机直连留空）"，但桌宠代码是：

```js
// electron/main.cjs:30
const SSH_HOST = String(localCfg.sshHost || 'pc');
```

**空串会回落成 `'pc'`，不是直连**（接口总览.md 不一致清单 D5 同此结论）。不过同机直连的正确姿势本来就绕开了这个字段：桌宠只在**探活失败**时才拉 SSH 隧道（`main.cjs:294` pingBridge 失败 → `main.cjs:322` spawn ssh），所以**让适配层直接监听 13100（tunnelLocalPort）即可同机直连，`sshHost` 填什么都不影响**（探活成功就不会去 ssh；回落 'pc' 连不上也无害）。预设方案按此写。

### 7.3 契合点

1. **私聊模型天然匹配**：桌宠的 `key = "private:<ownerQQ>"` 本质是"同一用户的固定私聊窗口"，MaiBot 的私聊聊天流（不填 group_info + `platform_io_target_user_id`）正是这个语义，上下文/记忆由 MaiBot 按 key 维护——正好落在 MaiBot 的强项（人格+记忆）上。
2. **"沉默是正常的"**：桌宠契约里 `reply:""` 不算故障，而 MaiBot 的回复时机本身是模型自决（"懂得在合适的时候开口，在合适的时候闭嘴"，README），两边语义吻合。
3. **短句、口语化**：MaiBot 的输出风格（非 markdown、或长或短的闲谈）适配桌宠气泡+语音朗读。
4. **插件/适配器双通道**：无论选外挂进程还是插件，都有官方文档与示例。

### 7.4 不契合点与对策

| 问题 | 说明 | 对策 |
|---|---|---|
| 同步 ≤90s vs 异步管线 | MaiBot 回复是异步推送（可能晚、可能多条、可能不回） | 适配层用"水位线 + 静默窗口"：注入后等待出站，收到第一条回复后再静默 ~4s 或到 80s 截止，把期间的文本 `join("\n")` 作为 `reply` 返回（正是桌宠文档"附 B·主动话术型"的水位线思路） |
| 自定义平台上主动开口程度未知 | `/recent` 可能总是空 | 按契约处理（空也合法）；要主动说话可用插件变体的 `ctx.maisaka.proactive.trigger()`，或由适配层在特定事件（如 `screen-permission`）注入文本让她自然接话（TODO 标注） |
| 语音 | 桌宠联机模式**没有系统 TTS 兜底**（接口总览.md §5.5 红色警告：不实现 `voice-preview` 就永远没声音） | 两个出路（原文）：① 后端实现 `voice-preview`（JSON `{ok,file 远端绝对路径}` + scp 可达）；② 改桌宠 `main.cjs` 约 10 行把 `petVoiceViaBridge` 失败分支接到现成 `synthSapi()`。骨架默认 ① 返回 `ok:false` 并留 TODO，方案文档写明 ② |
| `screen-permission` | 桌宠不传截图；且从不发送 `watch:false`（不一致清单 D4，停看靠文本「别看了」） | 适配层记录开关即可；"看屏幕"语义（截屏给模型）在 MaiBot 侧没有现成挂点，标 TODO |
| GPL-3.0 | MaiBot 是 GPL-3.0；外挂适配器经网络接口调用、不链接其源码，一般不构成衍生作品，但分发整体方案时注意许可 | 方案中注明 |

### 7.5 推荐接法（结论）

**推荐：外挂薄适配进程（路线 A）**——一个 Python 文件实现 5 个桌宠接口，经 `maim_message` 经典 WS（`ws://127.0.0.1:8000/ws`，默认开启）注入私聊消息并收集回复。理由：
- 直接基于官方"最小适配器"模式（文档自带可运行示例），API 面最小、与主程序唯一的耦合是协议版本（`maim_message==0.6.8` 与主程序钉死同版）；
- 独立进程故障隔离：适配层崩了不影响 QQ 侧；
- 插件方案（路线 B）虽是现行标准、部署更省事，但①所有第三方插件共享一个 Runner 子进程，插件崩溃会连坐 QQ 连接器；②本骨架未经真实环境联调，插件 API（manifest/capabilities）一旦与 1.3.15 有出入排查成本更高。故作为**备选**同样给出骨架。
