## 2. 插件机制

### 2.1 插件的形态（v4 现行，来自官方指南 + 真实插件源码双重验证）

一个插件 = `data/plugins/<插件名>/` 目录，最少三个文件：

```
data/plugins/astrbot_plugin_xxx/
├── main.py            # 插件类，文件名必须 main.py（wiki 旧指南："插件类所在的文件名需要命名为 main.py"）
├── metadata.yaml      # 元数据，AstrBot 识别插件依赖它（新指南 WARNING 原文）
├── _conf_schema.json  # 可选：配置 schema，声明后在 WebUI 可视化配置
├── requirements.txt   # 可选：插件第三方依赖（pip 格式）
└── logo.png           # 可选
```

`metadata.yaml` 字段（官方模板 https://github.com/Soulter/helloworld 的 metadata.yaml 原文 + 新指南）：
```yaml
name: helloworld          # 唯一识别名，推荐 astrbot_plugin_ 前缀
display_name: helloworld  # 展示名（>= v4.5.0）
desc: AstrBot 插件示例。
version: v1.3.0           # 格式 v1.1.1 或 v1.1
author: Soulter
repo: https://github.com/Soulter/helloworld
# 可选新字段：short_desc、support_platforms（ADAPTER_NAME_2_TYPE 的 key 列表）、
#   astrbot_version（PEP 440 版本范围，如 ">=4.16,<5"，不满足则阻止加载）、skills/ 目录
```
来源：https://raw.githubusercontent.com/wiki/AstrBotDevs/AstrBot/zh-dev-star-plugin-new.md （"声明支持平台" / "声明 AstrBot 版本范围" 节）；https://raw.githubusercontent.com/Soulter/helloworld/master/metadata.yaml

`main.py` 最小骨架（helloworld 模板原文摘录）：
```python
from astrbot.api.event import filter, AstrMessageEvent, MessageEventResult
from astrbot.api.star import Context, Star, register
from astrbot.api import logger

@register("helloworld", "YourName", "一个简单的 Hello World 插件", "1.0.0")
class MyPlugin(Star):
    def __init__(self, context: Context):
        super().__init__(context)

    async def initialize(self):
        """可选：实例化后自动调用的异步初始化。"""

    @filter.command("helloworld")
    async def helloworld(self, event: AstrMessageEvent):
        yield event.plain_result("Hello!")

    async def terminate(self):
        """可选：插件被卸载/停用时调用。"""
```
来源：https://raw.githubusercontent.com/Soulter/helloworld/master/main.py ；生命周期钩子 `initialize`/`terminate` 亦见源码 `astrbot/core/star/base.py:141,144`。

注意：官方 wiki 旧指南标题为「插件开发指南（旧）」，开头明确 *"此指南在 v4.5.7 之后已过时，请参考新的插件开发指南 [zh-dev-star-plugin-new]"*；但经与 helloworld 模板、市场插件（CS2 插件 `Aut-sep/Astrbot-plugin-CS2-match-push` 的 main.py:31 `from astrbot.api.star import Context, Star, StarTools, register`）比对，**Star/register/metadata.yaml 这套核心机制未变，旧指南中的 API 章节仍被官方标注"您仍然可以参考此页进行插件开发"**。
来源：https://raw.githubusercontent.com/wiki/AstrBotDevs/AstrBot/zh-dev-star-plugin.md （开头 WARNING 块）

### 2.2 关于「@register 在 v3.5.20 后废弃」的查证结论

网络搜索摘要中有说法称 *"v3.5.20 之后 @register 插件注册装饰器已废弃"*——**未在官方文档中找到该说法**；实测 v4.29 的官方模板 helloworld/main.py 与市场在审插件均在用 `@register(...)`，`astrbot/api/star/__init__.py` 源码中明确导出 `register_star as register`。判断：`@register` 是现行标准写法，废弃一说无来源支撑（可能混淆了旧版 `register_star` 装饰器签名或 v2 时代的写法）。
来源：https://raw.githubusercontent.com/AstrBotDevs/AstrBot/master/astrbot/api/star/__init__.py

### 2.3 插件能不能起自己的 HTTP 服务？——能，三条路

**路 A（本方案采用）：插件内用 aiohttp 自起独立端口**
- aiohttp 是 AstrBot 核心依赖（pyproject.toml `aiohttp>=3.11.18`），插件 `import aiohttp` 零额外安装。
- 真实先例：市场插件 `Aut-sep/Astrbot-plugin-CS2-match-push` 的 `web_panel.py`（521 行）——`from aiohttp import web`（第 16 行）、`self.app = web.Application(middlewares=[...])`（第 70 行）、启动 `web.AppRunner(self.app)` → `await runner.setup()` → `web.TCPSite(self._runner, host, port)` → `await new_site.start()`（第 497-513 行）。
  来源：https://raw.githubusercontent.com/Aut-sep/Astrbot-plugin-CS2-match-push/main/web_panel.py
- 该插件于 2026-03 提交 AstrBot 官方插件市场审核（AstrBot issue #6740，https://github.com/AstrBotDevs/AstrBot/issues/6740 ），说明"插件内自起 HTTP 服务"是被官方接受的模式。
- 生命周期：在 `initialize()` 里起 runner，在 `terminate()` 里 `await runner.cleanup()`（对齐 Star 基类钩子，base.py:141,144）。

**路 B：把路由挂进 AstrBot 自带 dashboard（`context.register_web_api`）——不适合桌宠**
- API 存在：`Context.register_web_api(route, view_handler, methods, desc)`，源码 `astrbot/core/star/context.py:764-786`。真实插件 `Zhalslar/astrbot_plugin_apis` 的 `page_controller.py:43-131` 就是这样注册了 20+ 条路由。
- 但 v4.29 源码显示这些路由的挂载点是 **`/api/v1/plugins/extensions/<plugin名>/<route>`**（`astrbot/dashboard/api/plugins.py:398-425` + `astrbot/dashboard/api/router.py:34` `API_V1_PREFIX = "/api/v1"`），且带 `Depends(require_plugin_scope)` 鉴权（dashboard JWT / API Key）。
- 结论：**路径前缀和鉴权都对不上桌宠的固定协议**（桌宠要打 `/api/status`、`/api/socialV2/pet-chat`，头是 `x-console-token`），所以不采用；仅作记录。
- 来源：https://raw.githubusercontent.com/AstrBotDevs/AstrBot/master/astrbot/dashboard/api/plugins.py ；https://raw.githubusercontent.com/Zhalslar/astrbot_plugin_apis/main/page_controller.py

**路 C（备选架构，不用插件）：直接对接 AstrBot v4.18+ 的 OpenAPI**
- AstrBot 自带 HTTP API：`POST /api/v1/chat`（SSE 流式，必填 `username`，可选 `session_id`）、`GET /api/v1/chat/sessions`、`POST /api/v1/im/message`（按 UMO 主动发消息）等；鉴权 `Authorization: Bearer abk_xxx` 或 `X-API-Key`，Key 在 WebUI `设置 → OpenAPI` 创建，支持 scope。
- 文档：https://raw.githubusercontent.com/wiki/AstrBotDevs/AstrBot/zh-dev-openapi.md ；交互式文档 `http://localhost:6185/api/v1/docs`。
- **适配桌宠仍需一个翻译层**（桌宠的路径/鉴权/同步等待语义是固定的），所以它不能独立满足需求；若不想写 AstrBot 插件，可写一个独立的小 HTTP 服务（如 FastAPI）翻译桌宠协议 → AstrBot OpenAPI。本预案主推路 A（一个插件全包），路 C 作为备选记录。

### 2.4 插件对消息平台的依赖

本方案的桥接插件**不依赖任何消息平台适配器**（不装 QQ/微信适配也能用）：pet-chat 直接调 `Context` 的 LLM API（见 §3），上下文由插件自己按 `key` 维护。这与桌宠接口文档附录 A「直接话术型」模式一致：*收到 pet-chat → 调你的模型 → 把输出放进 reply 返回，上下文由你自己按 key 维护*。
来源：D:/denia/娅娅桌宠-v1.0-内存优化版/docs/桌宠对接接口文档.md（「附：两种实现模式」A 节，本 ask 给定材料）

## 3. 插件里怎么调用 LLM

### 3.1 现行推荐（v4.5.7+）：Context 直接暴露的三个方法

官方指南（wiki「AI」页）原文示例：
```python
umo = event.unified_msg_origin
provider_id = await self.context.get_current_chat_provider_id(umo=umo)   # v4.5.7+

llm_resp = await self.context.llm_generate(chat_provider_id=provider_id, prompt="Hello, world!")
# llm_resp.completion_text

llm_resp = await self.context.tool_loop_agent(event=event, chat_provider_id=prov_id,
    prompt="...", system_prompt="...", tools=ToolSet([...]), max_steps=30)
```
来源：https://raw.githubusercontent.com/wiki/AstrBotDevs/AstrBot/zh-dev-star-guides-ai.md （「获取当前会话使用的聊天模型 ID」「调用大模型」「调用 Agent」节）

**源码签名核对**（`astrbot/core/star/context.py`，本会话下载后 sed 读取）：
- `llm_generate(self, *, chat_provider_id, prompt=None, image_urls=None, audio_urls=None, tools=None, system_prompt=None, contexts=None, **kwargs) -> LLMResponse`（context.py:180-219；docstring 注明 *versionadded:: 4.5.7*；内部就是转调 `prov.text_chat(...)`，见 context.py:209-218）
- `tool_loop_agent(self, *, event: AstrMessageEvent, chat_provider_id, ..., system_prompt=None, contexts=None, max_steps=128, tool_call_timeout=120, ...)`（context.py:224+）——**必填 event**，所以不适合"HTTP 进来的无 event 请求"直接用。
- `get_current_chat_provider_id(self, umo: str) -> str`（context.py:366）——内部走 `get_using_provider_async(umo)`，找不到就抛 `ProviderNotFoundError`。

### 3.2 本骨架采用的调用方式（无需 event，带 system_prompt）

**`Provider.text_chat()`**（旧指南「AI → 通过提供商调用 LLM」节，官方标注仍可用）：

```python
prov = await self.context.get_using_provider_async(umo=event.unified_msg_origin)  # umo 可省略
llm_resp = await prov.text_chat(
    prompt="Hi!",
    context=[{"role": "user", "content": "..."}, {"role": "assistant", "content": "..."}],
    system_prompt="You are a helpful assistant.",
)
print(llm_resp.completion_text)
```
来源：https://raw.githubusercontent.com/wiki/AstrBotDevs/AstrBot/zh-dev-star-plugin.md §AI（第 1232-1260 行）

**master 源码签名**（`astrbot/core/provider/provider.py:100-114`）：
```python
async def text_chat(self, prompt=None, session_id=None, image_urls=None, audio_urls=None,
    func_tool=None, contexts: list[Message] | list[dict] | None = None,
    system_prompt=None, tool_calls_result=None, model=None, ...)
    -> LLMResponse
```
要点：
- **`contexts` 接受 `list[dict]`**（OpenAI 风格 `{"role","content"}`），插件可以用纯 dict 维护历史。
- ⚠️ **参数名以源码为准：`contexts`，不是 wiki 旧指南示例里的 `context`**。master 的 `text_chat` 签名（provider.py:107）与 docstring（"contexts: 上下文，和 prompt 二选一使用"）均为 `contexts`；签名里有 `**kwargs`，传 `context=` 会被**静默吞掉**导致历史丢失。旧 wiki 示例的 `context=` 写法不可照抄。
- **`prompt` 和 `contexts` 可以同时传**：docstring 明确 *"如果都指定，则会将 prompt（以及可能的 image_urls）作为最新的一条记录添加到 contexts 中"*——正好匹配"历史 + 本轮输入"的用法。
- `system_prompt` 原生支持 → 桌宠的"人设"直接注入。
- `image_urls: list[str]` 支持文件路径（旧指南原文：*"支持文件路径"*）→ 桌宠传来的图片可透传。
- 获取 provider：`await self.context.get_using_provider_async()`——**umo 参数可空**（context.py:519 签名 `umo: str | None = None`），无消息平台/无 event 也能拿默认 provider；按 ID 取用 `self.context.get_provider_by_id(provider_id)`（context.py:452，同步，找不到返回 None 并告警）。

新旧取舍：`llm_generate` 是官方新推荐，但需要 `chat_provider_id`；拿 ID 的官方路径要么给合法 umo（HTTP 场景没有），要么 `get_using_provider_async()` 后取 `prov.meta().id`（context.py:371 内部即这么取）。骨架优先用 `get_using_provider_async()` / `get_provider_by_id()` 拿到 provider 后直接 `text_chat`，少一层转换、且 `contexts` 用纯 dict 更简单；在代码注释里同时标注了 `llm_generate` 的等价写法。

## 4. 插件的配置与鉴权

### 4.1 插件怎么读自己的配置（官方机制，非环境变量）

- 插件目录放 `_conf_schema.json`（JSON Schema 风格），AstrBot 自动解析并保存到 **`data/config/<plugin_name>_config.json`**，实例化插件时作为第二个参数传进 `__init__`。
- `AstrBotConfig` 继承自 dict，直接 `config["key"]` 读，`config.save_config()` 持久化。
- Schema 字段：`type`（必填：string/text/int/float/bool/object/list/dict/template_list/file）、`description`、`hint`、`obvious_hint`、`default`、`items`、`invisible`、`secret`（界面密码框遮罩，仅遮显示不改存储）、`options`、`slider`、`_special`（v4.0+，可选 provider/persona/知识库的 WebUI 选择器）…
- 用户改配置后在 WebUI 插件卡片点"重载插件"生效（运行时注入 + 热重载）。

来源：https://raw.githubusercontent.com/wiki/AstrBotDevs/AstrBot/zh-dev-star-guides-plugin-config.md （「配置定义」「在插件中使用配置」节，268-284 行原文）；
真实插件 `__init__(self, context: Context, config=None)` 写法见 CS2 插件 main.py:67 与 helloworld 新版模板。

**ask 里提到的 "config.yaml / ASTRBOT_ 环境变量"：官方插件机制里没有这两种方式**——查到的现行机制只有上述 `_conf_schema.json` + `data/config/<plugin_name>_config.json`（持久化数据目录是 `data/`，插件自读自写 yaml 也可以但不是官方面板集成的路）。AstrBot 核心的主配置在 `data/cmd_config.json`（管理面板读写它），插件不应直接改。此点如实说明，不编造环境变量机制。

### 4.2 鉴权

- **插件自己的 HTTP 服务自己鉴权**：本方案在插件里校验请求头 `x-console-token` 与插件配置 `console_token` 相等（HMAC 级别的常量比较用 `hmac.compare_digest`），未配置 token 时拒绝服务。AstrBot 不会替插件的独立端口做任何鉴权。
- 若走路 B（dashboard 挂载），鉴权是 dashboard 的 JWT/API Key（`require_plugin_scope`，plugins.py:398+），与 `x-console-token` 无关——已排除。
- AstrBot OpenAPI（路 C）的鉴权是 `Authorization: Bearer abk_xxx` / `X-API-Key`（zh-dev-openapi.md）。

### 4.3 持久化

- 官方开发原则：*"持久化数据请存储于 data 目录下，而非插件自身目录，防止更新/重装插件时数据被覆盖"*（新指南「开发原则」节）。
- 桌宠桥接的会话历史 v1 先放内存（进程重启即清空，可接受）；要持久化可写 `data/plugin_data/astrbot_plugin_pet_bridge/history.json`（`get_astrbot_plugin_data_path()`，源码 `astrbot/core/utils/astrbot_path.py:60`）。骨架里预留了 TODO 注释。

## 5. 桌宠协议 ↔ AstrBot 能力的映射（结论表）

## 6. 未查证 / 不确定项（如实列出）

1. **骨架未在真实 AstrBot 实例中端到端跑通**——本会话环境约束（不装运行时、不起服务，桌宠应用也在别处运行）。已做的验证：
   - Python 3.12.10 `py_compile` 语法验证通过、`_conf_schema.json` 过 `json.tool`、`metadata.yaml` 过 PyYAML 解析；
   - **桩环境冒烟测试 12/12 通过**：用替身模块顶替 `astrbot.*`（只替 import 面，HTTP 层用真实 aiohttp 3.14.5），真实起服后按协议打全部 5 个接口——探活 200、无/错 token 401、空 text 400、正常回复（含 system_prompt 注入与按 key 累积的历史）、recent 恒空 + 扩展通道、screen-permission 回执、voice-preview 桩。结果以 `PASS/FAIL` 逐条输出，共 12 项全过。**这不等于真实 AstrBot 运行时验证**（`Provider.text_chat`、`get_using_provider_async` 等调用点只做了源码签名核对，没有真跑）。装上真机后的第一件事是按预设方案 §6 验收。
2. `provider.text_chat` 对 `data:image/png;base64,...` 形态 image_urls 的兼容性未实测（OpenAI 兼容端一般支持 data URL，但各 Provider 实现不一），骨架里标了 TODO 并做了格式归一。
3. 桌宠对 `voice-preview` 返回 `ok:false`（而非 404/不实现）时的具体表现，接口文档未写明——骨架按"返回 ok:false"实现，若真机出现错误气泡，注释掉该路由让它 404 即等价于"不实现"。
4. 插件配置热重载时 aiohttp 端口的重绑定细节（CS2 插件 web_panel.py:497-513 显示它支持同 runner 换站点重绑，骨架采用"terminate 后重建"的更简单策略，未测热重载）。
5. 未逐条核对新指南系列的所有子页面（如插件国际化 i18n、Skills 子页），与本任务无关故略过。
6. web_search 摘要中 "v4.5.7 LLM 调用方式重大改进" 已被官方文档证实（wiki AI 页："我们在 v4.5.7 版本之后对 LLM 提供商的调用方式进行了较大调整"）；"v3.5.20 @register 已废弃" 未找到来源，判定为不可信（§2.2）。
